NARRATION:

SLIDE 6 — Step 4: Copy Blockchain Smart Contract Details
════════════════════════════════════════════════════════════════════

ON SCREEN:
  Terminal — SSH into Pi or use serial console

COMMANDS:
  # From build machine — copy blockchain config to Pi
  scp /path/to/contract_address.txt  root@<pi-ip>:/etc/iot-gateway/
  scp /path/to/abi.json              root@<pi-ip>:/etc/iot-gateway/
  scp /path/to/wallet_key.txt        root@<pi-ip>:/etc/iot-gateway/

  # On Pi — verify files are in place
  ls -la /etc/iot-gateway/
  cat /etc/iot-gateway/contract_address.txt

  # Restart service to pick up config
  systemctl restart iot-gateway
  journalctl -fu iot-gateway

NARRATION:
  "The blockchain logger needs three things: the deployed smart contract address
   on the Ethereum network, the contract ABI so it knows how to call functions,
   and the wallet private key used to sign transactions.
   These are copied to the protected /etc/iot-gateway directory on the Pi's
   rootfs. After restarting the service, the log shows the Ethereum node
   is reachable and the contract is loaded."

BACKEND:
  BlockchainLogger constructor reads these files
  Establishes JSON-RPC connection to Ethereum node
  Calls checkConnectivity() — verifies eth_blockNumber responds
  Logs: "[Blockchain] Connected to Ethereum node, contract loaded"

WHAT TO SHOW:
  journalctl output confirming blockchain connectivity

  3. Point camera at QR code on browser screen
  4. Account "RaceIoT-Gateway:paneldemo" appears in the app
  5. A 6-digit rotating code is shown (refreshes every 30 seconds)

NARRATION:
  "I open Google Authenticator on my phone and scan the QR code.
   The app decodes the otpauth URI and stores the TOTP secret locally
   on the phone. It immediately begins generating time-based one-time
   passwords — a new 6-digit code every 30 seconds using HMAC-SHA1
   over the current Unix timestamp divided by 30.
   This secret never leaves the phone after initial setup."

BACKEND:
  QR encodes: otpauth://totp/RaceIoT-Gateway:paneldemo?secret=BASE32SECRET&issuer=RaceIoT-Gateway
  Phone app decodes Base32 secret
  TOTP algorithm: HOTP(secret, floor(time/30)) truncated to 6 digits
  Server stores same secret via UserAuth::registerUser()

WHAT TO SHOW:
  The 6-digit code ticking down on the phone
  Point out the 30-second countdown ring in the app

SLIDE 14 — Security Feature: Lockout Demo (Optional but impressive)
════════════════════════════════════════════════════════════════════

ON SCREEN:
  Browser — Login page

ACTION:
  1. Enter wrong password 3 times for user "paneldemo"
  2. Show the countdown lockout modal (30-minute timer with progress bar)
  3. Show the blockchain log: LOCKOUT event emitted after 3rd failure

NARRATION:
  "To demonstrate brute-force protection: three wrong passwords trigger
   a 30-minute account lockout. The lockout modal shows an animated
   countdown timer. Critically — individual failed attempts are NOT
   written to the blockchain each time, to avoid gas costs from
   automated attacks. Only when the threshold is crossed does a single
   immutable LOCKOUT event get recorded on-chain.
   The same lockout applies to the OTP phase — three wrong codes also
   lock the account."

BACKEND (show log):
  [LOGIN] FAILED password for 'paneldemo' (1/3)
  [LOGIN] FAILED password for 'paneldemo' (2/3)
  [LOGIN] FAILED password for 'paneldemo' (3/3)
  [BLOCKCHAIN] LOCKOUT logged (password threshold) for 'paneldemo'

WHAT TO HIGHLIGHT:
  Only ONE blockchain line for 3 failures (gas-efficient design decision)
  The animated progress bar counting down

SLIDE 15 — Security Feature: mTLS Demo (Optional)
════════════════════════════════════════════════════════════════════

ON SCREEN:
  Two terminal windows side by side

LEFT TERMINAL — Attacker (no cert):
  curl --insecure --verbose https://<pi-ip>:8443/
  # Shows: SSL_connect: Connection reset — NO HTTP response

RIGHT TERMINAL — Authorised client:
  curl --insecure --verbose \
       --cert ~/mtls-demo/client-authorised.crt \
       --key  ~/mtls-demo/client-authorised.key \
       https://<pi-ip>:8443/
  # Shows: HTTP/1.1 200 OK — landing page received

NARRATION:
  "This is mutual TLS in action. On the left — a direct connection
   without a client certificate. GnuTLS rejects it at the handshake —
   no HTTP data is ever transmitted. The attacker cannot even see the
   login page. On the right — a client presenting a certificate signed
   by our Root CA gets through immediately. In production, only cloudflared
   holds this certificate."

Pi log shows:
  Left: nothing (connection never reaches MHD layer)
  Right: Handling GET request for URL: /
